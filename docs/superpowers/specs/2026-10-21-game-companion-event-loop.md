# 事件驱动游戏助手闭环：现有能力整合与缺口

**状态：** 架构补充与差距分析；不代表本文所列全部能力已经完成验收  
**日期：** 2026-10-21  
**关联：** [独立软件改造计划](../../transformation-plan.md)、[UI/UX 设计规范](../../ui-ux-design-spec.md)、[未来扩展](../../future-extensions.md)

## 1. 目标

把此前讨论的 AI 金手指、游戏状态副屏、自动捕捉精彩时刻、内存变化触发 AI、存档分析和可复用 Game Profile 统一成一个产品闭环，而不是拆成互相独立的工具。

核心原则：

> **由确定性软件层持续采集被允许的状态、发现事件并保存证据；AI 只在有意义的事件发生后按策略参与分析。** 不要求 AI 每帧感知，也不把持续采集变成持续模型调用。

本文件用于对照现有代码、明确尚未闭合的行为，并为后续实现提供单一的集成方向。

## 2. 已有能力与真实缺口

| 能力 | 现有实现 | 尚需补齐的关键点 |
|---|---|---|
| 游戏状态模型 | `TCEAGameStateModel`、`TCEAGameField`、版本指纹 | 采集调度、字段刷新状态与目标身份变更的统一处理 |
| 字段采集 | `TCEAStateCaptureService`、`CaptureFieldValue` | 当前采集服务只有一个全局上次值，交替采集不同字段会产生错误的 Changed 结果；没有配置字段的后台定时采样闭环 |
| 变化触发 | `TCEAEventService.ObserveField`、规则、冷却、事件合并 | 规则只有在字段被调用采集时才会评估；需由明确启停、限额的采样器驱动 |
| 事件证据 | 字段快照、事件包、SQLite 事件存储、事件分析 | 把字段变化、录制帧、Profile 版本和来源证据关联为统一事件包 |
| 视频/帧捕获 | `TCEAWin32WindowFrameSource`、`TCEAWin32RecordingCapture` | 当前 `CaptureSegment` 在事件发生时才抓取帧，并在循环中立即重复抓取；不能保证真正的事件前预录、后录或正确帧间隔 |
| 录像缓存 | `TCEARecordingService` 管理片段元数据、锁定与淘汰 | 元数据缓存不等于持续帧环形缓存；需要有界、带真实采集时间戳的滚动缓冲和异步片段封装 |
| AI 唤醒 | `TCEAEventWakeQueue`、`MarkAnalysisState(eaQueued)`、事件分析服务 | 队列目前只排队，不自动调用模型；需要明确区分“自动入队”“本地分析”“云端发送”，不允许默认静默外发 |
| 副屏 | `TCEASecondaryScreenHost`、UI Schema Runtime、本地授权写入回调 | 将事件时间线、捕获证据和当前字段投影组合起来；副屏不能成为第二份权威状态 |
| AI 金手指 | 扫描、假设、验证、Recipe、受治理写入 | 事件/AI 建议只产生下一步观察或假设，不直接授予写权限；写入继续走现有 Approval/Effect/Readback/Proof |
| 存档 | 格式无关只读快照、备份；仅项目自有 fixture Codec 可写 | 未验证的真实游戏格式继续只读/备份；每个游戏版本需单独验证 Codec |
| CT 知识库 | 本地解析、来源、哈希、检索/RAG | 检索结果是 Evidence，不是事实、可执行脚本或权限；不要把未知来源内容自动执行 |

### 2.1 两个必须先纠正的语义

1. **字段变化不是持续监控。** `ObserveField` 能确定性地比较相邻快照，但如果没有调度器持续调用采集，它不会凭空观察到游戏变化。当前 UI 的 15ms pump timer 主要用于处理 LLM/扫描任务和命令队列，不是游戏字段采样器。
2. **事件发生后重复抓帧不等于事件前后录像。** 事件前的画面必须在事件发生前已经存在于滚动缓存中；事件后的画面需要等待后录窗口结束后再封装。帧的时间戳必须来自真实抓取时刻，不能用请求的窗口时间冒充。

## 4. 字段采样器设计

新增的采样器应是确定性服务，不依赖 LLM。

### 4.1 采样对象

只采集用户当前 Profile 中明确启用的字段。每个字段至少绑定：

- 稳定的 `field_id`、类型、当前定位方式及来源；
- 游戏 EXE 哈希、模块集哈希、ProcessIdentity ID 和 Epoch；
- 采样间隔、上次成功值、上次成功时间、最近错误；
- 该字段的证据等级与可读/可写状态。

目标进程身份或 Epoch 改变时，立即停止旧采样会话、清空比较基线并要求重新验证定位。绝不把旧进程的地址或快照延续到新身份。

### 4.2 预算与调度

- 默认关闭自动采样；由用户对具体游戏会话显式启用。
- 仅采集 Profile 已选字段，不进行后台全进程扫描。
- 设置每轮字段数、最小采样间隔、每轮最大读取字节、每分钟读取预算和最长运行时间。
- 使用后台 worker 与不可变状态投影，不能阻塞 Lazarus UI 或 MCP HTTP 线程。
- 失败读取要记录为缺失/过期状态，不得把旧值伪装成新鲜值。
- 字段差分只触发本地规则，不直接调用模型。

## 5. 真正的事件前后捕获

### 5.1 帧环形缓冲

录像开启后，捕获线程按配置间隔持续采集当前游戏窗口的帧，并将帧与元数据写入有界滚动缓冲。每帧至少记录：

- 单调时钟时间戳、序号、尺寸、像素格式；
- 捕获结果、帧哈希或可检测损坏的完整性信息；
- 对应的 ProcessIdentity / 窗口身份；
- 存储位置和实际字节数。

缓冲按**真实时间范围和实际字节数**淘汰最旧的未锁定帧。预算达到上限时必须显示丢帧/覆盖情况，不能假装连续。

初版可以先交付关键帧序列与可回放的时间线；若未实现视频编码，不得把帧序列宣传为完整 MP4 视频。后续编码器是独立组件，须单独验证许可证、资源占用和失败恢复。

### 5.2 事件窗口生命周期

事件不能同步阻塞采样线程或 UI。建议状态：

- `pending_pre_roll`：事件创建，引用触发时刻之前仍在环形缓冲中的帧；
- `capturing_post_roll`：在有界后录时长内继续接收新帧；
- `finalizing`：冻结帧引用、字段快照和事件元数据；
- `ready`：可在本地时间线查看或提交分析；
- `partial`：捕获不可用、帧缺失、预算耗尽或窗口身份失效；
- `cancelled` / `deleted`：用户取消或删除。

事件合并时延长同一个事件的后录截止时间并合并字段差分，不要对同一时间窗口重复复制整段录像。所有时间都来自单调时钟；显示用墙上时间单独存储，不能把两种时间基准混算。

### 5.3 Windows 捕获限制

当前 GDI 窗口抓帧是原型后端，不保证在所有硬件加速、遮挡、最小化、HDR 或独占全屏游戏中正常工作。必须通过能力探测和运行时状态说明限制。失败时事件和字段证据仍应保存，但录像引用应为空或标记为 partial；不能谎报录制成功。

## 6. “自动录像 ≈ 自动给 AI 提示词”的落地方式

真正传给模型的不是一整段未经处理的录像，而是一个有来源、有预算的事件上下文包：

- 事件触发原因与单调时间范围；
- 当前游戏/Profile 指纹；
- 相关字段的前值、当前值、变化方向、采集时间与证据引用；
- 事件前后的帧引用，以及本地生成的缩略图/关键帧（仅在用户允许时提供给视觉模型）；
- 相关 CT 条目、存档快照或攻略文档的来源引用；
- 明确区分观察事实、用户陈述和 AI 假设；
- 建议的下一步只读观察，以及预算/缺失证据说明。

### 6.1 唤醒策略

建议显式分为三个设置，默认使用最保守策略：

1. **Manual（默认）**：自动采集与事件记录；用户点击后才分析。
2. **Auto-enqueue**：符合本地规则的事件自动入队；模型调用仍由用户确认。
3. **Auto-analyze**：仅在用户对当前会话明确启用、预算上限和数据范围均已配置时使用。任何向云端发送内存值、截图或事件摘要的请求，仍需满足当前项目的逐次云端同意门禁；不得因为打开了录像就默认同意外发。

队列满、模型不可用或模型超时不能阻塞采样与录像，也不能删除原始事件证据。模型生成的建议永远不能直接触发内存写入、存档写入、脚本执行或提高授权范围。

## 7. 副屏、金手指与事件时间线的统一

副屏继续采用 `TCEAGameStateModel → UI Schema → Secondary Screen Host`：

- 状态展示只读当前的状态投影，显示来源、更新时间、验证状态和不确定性；
- 只有已验证为 `verified_writable` 的字段才允许生成提交控件；
- 所有编辑经现有 Command Bus、审批、compare-write-readback 和 Proof，不允许网页直接操作内存；
- 事件时间线应能打开关联帧、字段差分、操作历史和相关证据；
- AI 自动生成的布局/字段映射必须先进入待确认状态，不能自动变成可信 Profile；
- 副屏通过本机回环服务访问，保留令牌验证、仅本机监听和撤销机制。

这让“副屏显示信息”“副屏修改信息”和“AI 解释刚才发生了什么”共用同一份状态与证据，而不是做三套互不一致的数据副本。

## 8. Game Profile 与分享边界

Profile 应可复用字段语义、指针链/签名定位规则、UI Schema、触发规则、采样预算与兼容性证据，并绑定游戏版本指纹。

分享包必须清理：

- 绝对内存地址、用户存档、录像帧、用户名和本地路径；
- API Key、Bearer Token、凭据引用和私人端点；
- 未经许可的 CT 文件内容与第三方知识库数据。

接收方导入 Profile 后，字段和写入状态默认需要重新验证；不继承原维护者的 Approval、Lease 或 `verified_writable` 授权。

## 9. 现有安全边界继续有效

- 只面向用户授权的离线单人游戏。
- 不支持多人游戏作弊、反作弊绕过、隐藏进程或内核驱动。
- CT/外部资料都是不可信输入，绝不自动执行。
- AI 的输出是 Hypothesis / ToolProposal，不是执行权限。
- 未知真实存档格式只读/备份；真实格式写入必须有独立验证的游戏版本 Codec。
- 录像默认关闭；本地保存、锁定、删除和保留期限均应可见。
- 采样/事件检测不能要求每帧调用 LLM，也不能把“自动唤醒”解释成“自动写入”。

## 10. 验收门槛

1. 交替采集两个字段时，首次采集均为 `changed=false`；同一字段不变时不误报变化，真正变化时能检测到。
2. 进程 PID 相同但身份 ID/Epoch 改变时，旧比较基线失效，必须重新建立。
3. 在没有启用采样的情况下，不发生周期性读取；启用后仅读取用户选定字段并严格遵守预算。
4. 触发事件时，事件前帧来自触发前的环形缓冲，后录帧时间晚于触发时刻；不允许用连续瞬时抓帧冒充时间间隔。
5. 帧窗口、事件时间线和字段快照共享单调时钟；事件合并不会重复复制片段。
6. 录像捕获不可用时，事件仍可保存字段证据并明确标记缺失/partial。
7. 队列满、AI 超时或取消不影响采样线程，不删除事件包。
8. 未逐次同意外发时，模型请求不能携带内存值、截图或事件包。
9. 副屏只允许展示已验证字段；写入仍须通过本机授权和独立读回验证。
10. 删除事件时按定义清理对应元数据与媒体文件；锁定/保留规则不得留下无法发现的孤儿媒体文件。
